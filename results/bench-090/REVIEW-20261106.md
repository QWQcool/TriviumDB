## v3 独立数值核对

全部 14 次完整组尝试、42 个成功运行的原始 JSON 已独立重算每个 ef 的样本 CV、建图离散度和目标召回插值，未发现与记录不一致。目标可达组的插值跨度均不超过 0.05；边界数据集 TriviumDB 的三张图均未达到 90% 目标，不能外推。所有 42 轮的 Job 退出码均为 0、终止后活跃进程数为 0，库指纹各轮前后检查与清单一致。入场门禁不等于持续背景负载证明。

## 查询波动诊断：仅诊断，不能用于发布

[预注册文件](diagnostic-query-20261106/preregistration.json) 固定 A/B/B/A/A/B 六次独立构建、每个固定索引对五个 ef 各测 10 次；[汇总](diagnostic-query-20261106/summary.json) 标记 `diagnostic_only` 且 `performance_publishable: false`。A 为 20,000 条平铺查询，B 是 A 的四份字节级复制、总长 80,000 条，**不是 80,000 条独立查询**。独立检查了全部 300 条批次记录、顺序、派生耗时、样本 CV、门禁、监督以及脚本快照哈希；生成的两个 B 文件各自的全文件哈希和四段哈希也已重新计算并匹配源输入。

按预注册方法排除每个 ef 的第一次观测后，固定索引内各 ef 的样本 CV 范围为 2.42%–7.36%；分别对每个条件的三张独立索引取各自中位数后，A 的跨索引样本 CV 为 12.25%–14.23%，B 为 4.75%–6.18%。这两种 CV 的统计单位不同，不能互相替代。A/B 使用不同独立索引，查询窗口、索引构建、运行顺序、缓存及温度等因素可能混杂；三张图的诊断不足以证明延长窗口导致稳定，也不能证明正式批次已通过。

每轮入场 CPU 采样和内存均满足当时门槛；观察期间系统总 CPU 包含基准进程。观察器进程 CPU 增量约 0.047–0.109 秒/轮，包含全部 Python 线程；采样墙钟包含主动等待，不能把墙钟误认成 CPU 开销。系统级频率/性能计数只在每轮前后采样，ACPI 温区原始值恒为 72 且未经校准，不能据此推导 CPU 封装温度、排除热影响或认定降频原因。输入、脚本快照、可执行文件及工作树补丁在记录边界保持绑定；脚本快照采于 Python 已导入源码之后，不能独立证明已加载字节与快照完全相同。

### 补充：事后探索

在 A 条件下，第一张索引的五个 ef 各自排除首批后的 9 次 QPS，最大值均低于第四轮和第五轮相同 ef 各自的最小值；相同 ef 的重复查询召回在每张索引内一致，但不同索引间不完全相同。六轮的 `hot_bytes` 相同，并不能证明索引拓扑相同。这说明观察到的差异不只是单个短批次的偶发尖峰；运行顺序、背景环境、缓存、索引结构和温度等仍有混杂，不能将其归因于某个因素。
## 其他测试与未解决事项

- 原版 P1 在两个规模均发生断言失败；已有补丁版分别跑通，但只比较选定字段的内容签名，不能宣称原断言或完整 `NodeSet` 相等通过。
- release 故障套件在 `fault_io` 编译时 rustc 发生访问异常，没有完成测试。分开执行的 debug 非 allocator 套件父测试汇总为 102 passed、1 ignored；独立 debug allocator 为 5 passed，含实际子进程检查。它们不能抵消 release 套件失败。
- 原始 RSS 长稳测试与单项诊断复验均未通过。Windows 工作集增长超出该测试阈值是可证事实；私有内存和工作集时间序列不足以确定内存泄漏或其他根因。复验观察器有额外开销，且本地诊断脚本在进程启动后曾修改、执行版本未事先哈希，见 [诊断溯源说明](replay-review-20261105/soak-diagnosis/PROVENANCE.md)。
- 若要恢复发布门禁，需先针对正式查询波动建立并预先固定新的可复核调查/重测方案，解决或如实处置其他测试失败，再根据通过的新批次修订白名单和统计说明，重新逐项审阅。没有通过前不制作 X 文案或图，也不把结果描述成全面通过。
