# T2 B2 设计 — 分区式图构建的端到端判定实验

> **目标**：判定"用分区受限候选替代全局束搜索"能否在**不损召回**的前提下**降低建图成本**。
> **前序**：`t2-pipnn-recon.md`（C1–C9、B1 通过）
> **状态**：设计文档（不含实现）。`src/` 仍未改动。

## 0. 目标与预注册判据

**主问题**：把 81% 成本的全局束搜索换成分区受限候选，能否达到基线召回，且成本更低？

**预注册判据**（先写死，避免事后找解释）：

| 判据 | 阈值 | 含义 |
|---|---|---|
| **P1 质量** | 分区版的 R@10（ef=128）**≥ 冻结基线 97.55% − 1.0pp** | 分区候选质量足够 |
| **P2 成本** | 分区版的**建图 CPU 时间 ≤ 基线 × 0.7** | 有真实收益 |
| **P3 双赢** | P1 ∧ P2 同时成立 | **只有 P3 才值得继续投入** |

**必须同时报告一个"平凡对照"**（见 §3 的 B2-0）：若仅调小 `ef_construction` 就能达到同样的
成本-质量点，则**分区化毫无意义**——这是本设计里最重要的一条防自欺机制。

## 1. 从代码新读到的两个事实（决定整个设计）

### 1.1 ★ 候选集 = 束搜索 **⊕ 128 个全库随机样本**

`connect_node_fast`（`quiver.rs:696-813`）的候选构造（`:710-730`）：

```rust
// ① 全局束搜索，宽度 ef（= ef_construction）
let candidates_sym = self.beam_search_l0_locked(&my_sig, 0, self.ef, visited);
let mut candidates = candidates_sym.filter(id != idx).map(distance).collect();

// ② ★ 额外注入 samples 个【全库】随机节点
let samples = self.ef.min(128).max(self.m0 * 2);   // m=32 ⇒ m0=64 ⇒ 恒为 128
for _ in 0..samples {
    let id = (xorshift(state) % self.n) as u32;    // 均匀随机，全库
    if id != idx { candidates.push((distance(idx, id), id)); }
}
// 之后：按 id 排序去重 → 按距离排序 → vamana_select(m0, alpha)
```

**三个直接后果**：

1. **`samples` 恒为 128**（`min(ef,128).max(128) = 128`，对任何 `ef ≤ 128`）。
   ⇒ 调整 `ef_construction` **不会**改变随机注入量 → **ef 扫描是干净的**（§3 B2-0）。
2. **纯分区内候选会丢掉长程覆盖**——随机注入提供的是"全库随机"的长程候选，
   与分区局部性正交。故 B2 的 A/B **必须保留随机注入**，只替换 ①。
   这既更忠实，也更有利（局部候选只需负责局部质量）。
3. **它解释了 C3 偏高的跨分区边率**：随机注入的 128 个候选里，约 `128/k` 落进本分区
   （k=16 时约 8 个），其余全在外部；它们与束搜索候选一起进入 `vamana_select` 竞争 64 个名额。
   ⇒ `t2-pipnn-recon.md` §4.4 的 B1 覆盖率**混合了两类来源的边**，这一点已在彼处声明。

### 1.2 ★ 修正 `t2-pipnn-recon.md` 的 C8（我高估了扫描成本）

C8 原文用"`ef×m0 ≈ 8192` 次/节点"作为基线成本，据此说扫描池"贵 38×"。**该基数偏低**。
从 `BuildProfile` 反推：

```
建图 CPU 964s × 81.35%(beam) = 784s        （1M 节点）
⇒ 784 μs / 节点 的束搜索时间
⇒ 若单次 BQ2 距离 ≈ 10 ns（AVX2），约 7.8 万次距离计算 / 节点
```

这与"展开 ≈ 1.2K 个节点 × 度 64 ≈ 7.7 万"自洽。**所以基线 ≈ 7.8 万次/节点**（标为**反推**，B2-0 会实测标定）。

| 方案 | 距离计算 / 节点 | 相对基线 |
|---|---|---|
| 基线（束搜索 ef=128 + 128 随机） | ~78,000 | 1.0× |
| 分区池**精确** top-128（k=16, J=3） | ~190,000（3 个分区 × 66K） | **2.4×** |
| 分区池**采样子集** top-128（cap=16K） | ~16,000 | **0.21×** |

⇒ **精确扫描是 2.4× 更贵，不是 38×**。C8 的定性判断（"PiPNN 必须靠摊销取胜"）仍成立，
但**量级要改**：摊销需要打掉的不是 38×，而是 **2.4×**，目标变得**现实得多**。

> C8 的勘误已同步到 `t2-pipnn-recon.md`。

### 1.3 注入点

`connect_node_fast` 的结构天然可切：

```
[候选获取]  beam_search_l0_locked(ef)  ⊕  128 随机        ← 只替换这一块
   ↓
[排序去重]  by id → dedup → by distance                    ← 不动
   ↓
[选边]      vamana_select(idx, cand, m0, alpha)            ← 不动
   ↓
[写正向边]  set_neighbors_locked_fast                      ← 不动
   ↓
[反向边]    惰性追加 / 容量满时 vamana_select              ← 不动
   ↓
[final_prune]                                              ← 不动
```

⇒ 下游（`vamana_select` / 反向剪枝 / `final_prune` / 序列化 / `search_flat`）**全部复用**，
A/B 的差异**只来自候选来源**。这是本设计可做的关键。

## 2. 缝合策略选型：选 **S2**

| 方案 | 做法 | 是否改搜索 | 评价 |
|---|---|---|---|
| **S1** | 每分区选代表点，建**全局粗图**，搜索经多入口路由 | **是**（需多入口遍历 + 路由逻辑） | 改动大；会把"建图"与"搜索"两个变量混在一起 |
| **S2** | **不加代表点**；构节点 `u` 时候选池取"`u` 的 J 个最近分区"的成员，跨区边自然涌现 | **否** | ✅ 单层全局 L0 图不变，`search_flat` 原样复用 |

**选 S2**，理由：

1. **它正是 B1 度量的那件事**（B1 已通过：`k=16/J=3` 覆盖率 91.4%）。
   设计与已验证的证据直接对应，不需要新假设。
2. **不改搜索** ⇒ B2 的 A/B 只变动一个变量（候选来源），
   且能直接复用冻结基线的 `search_flat` + `QUIVER_VERSION=1` 序列化格式（**零格式改动**）。
3. S1 的多入口改动（M1）会连带改 `entry_point` 语义、序列化、`search_flat`，
   属于 B2-2 之后才该碰的范围。

> **代价**：S2 无法缓解 C4 的分区不均衡（负载失衡仍在候选**扫描量**上体现）。
> 但 S2 下扫描量只与"J 个分区的成员总数"有关，失衡会被均值化；真正的失衡风险留给 B2-2。

## 3. 分阶段实验矩阵

**关键设计原则：先用最便宜的手段证伪。**

### B2-0（**零代码**）：`ef_construction` 扫描 —— 平凡对照 ★ 必做且最先做

`QuIVerConfig.ef_construction` 是 `pub` 字段（`quiver.rs:951`），改它**不需要任何代码改动**。

| 臂 | ef_construction | samples（随机注入） |
|---|---|---|
| A0 | 128（基线） | 128 |
| A1 | 64 | 128 |
| A2 | 32 | 128 |
| A3 | 16 | 128 |

（`samples = min(ef,128).max(128) ≡ 128`，与 ef 无关 ⇒ **纯扫束搜索宽度**）

**判定**：若 **A2（ef=32）的 R@10 ≥ 97.55% − 1pp**，则
**81% 的束搜索成本可以靠一个配置项砍掉 4×，PiPNN 的靶点直接消失** ⇒ **整条线停止**。

这一臂的成本是 **0 行代码 + 4 次建图（约 4×40s）**。
**它是本设计里性价比最高的一步，必须先跑。**

### B2-1（**小改，约 60 行**）：分区受限精确候选

在 B2-0 确定"ef 不能小"之后，替换候选来源 ①：

| 臂 | 候选来源 ① | 随机注入 ② | 池规模 |
|---|---|---|---|
| B0 | 束搜索 ef=128 | 128 全局随机 | — |
| B1 | **分区池精确 top-128**（k=16, J=3） | 128 全局随机 | ~190K → **2.4× 成本** |
| B2 | 分区池**采样** top-128（cap=32K） | 128 全局随机 | 32K → 0.41× |
| B3 | 分区池**采样** top-128（cap=8K） | 128 全局随机 | 8K → 0.10× |

**判定**：
- **B1 召回达标** ⇒ 质量前提成立，剩下纯成本问题 ⇒ 进 B2-2（摊销）
- **B1 召回不达标** ⇒ 分区局部候选质量不足 ⇒ 停止（B2/B3 只会更差，因采样是单调劣化）

> B1 用**精确** top-128 是"分区内能做的最好情况"的上界；B2/B3 是成本优化方向。

### B2-2（**仅 B2-1 通过后**）：摊销版

PiPNN 的真正机制：**每个分区只建一次局部图，分区内全部节点复用**，
把 2.4× 的扫描成本摊掉。实现需新增分区局部图结构（M2 的扩展）。
**前置**：B2-1 必须证明质量够（否则摊销一个坏图没有意义）。

### 不在 B2 范围

- 多入口 / 粗图路由（S1）——留给 B2-2 之后
- 序列化分区表（M6）——B2 全程**只用内存态**，`QUIVER_VERSION` 保持 1
- k 的大范围扫描（B3）——B1 已给出 `k=16/J=3` 为当前最优折中

## 4. 代码改造设计（B2-1）

> 目标：**新增为主、改动最小、完全可逆**。所有新代码走 `#[cfg(feature = "ablation")]` 或新入口，
> 不触碰任何现有生产路径的行为。

### 4.1 新增：`PartitionCtx`（`src/index/quiver.rs` 内新增，约 50 行）

```rust
/// B2 实验：分区受限候选池。
/// 由外部（Python 预计算的 k-means 结果）提供，故构建逻辑不进入生产代码。
#[cfg(feature = "ablation")]
struct PartitionCtx {
    /// 每节点的分区 id（长度 n）
    assign: Vec<u32>,
    /// part_rank[u*k + p] = 分区 p 在"离 u 的质心距离序"中的名次（u16，k ≤ 32767）
    part_rank: Vec<u16>,
    k: usize,
    /// 候选池 = u 的 top-J 分区；J=3 时覆盖率 91.4%（B1 §4.4）
    j: usize,
    /// 按分区分组的成员 CSR（由 assign 一次计数排序得到）
    part_off: Vec<u32>,
    part_members: Vec<u32>,
    /// 采样上限：usize::MAX = 精确扫描全池
    pool_cap: usize,
}

#[cfg(feature = "ablation")]
impl PartitionCtx {
    fn build(assign: Vec<u32>, part_rank: Vec<u16>, k: usize, j: usize, pool_cap: usize) -> Self { ... }

    /// 返回 (距离, id)，按距离升序，长度 ≤ topk。
    /// 语义与 `beam_search_l0_locked` 的输出**完全同型**，可直接替换。
    fn topk_in_pool(
        &self, idx: u32, sigs: &Bq2Store, dim: usize, topk: usize,
    ) -> Vec<(NonNanF32, u32)> { ... }
}
```

`topk_in_pool` 的做法：遍历 `part_rank[idx*k .. idx*k+k]` 找出 `< j` 的分区并集 →
顺序扫描这些分区的成员 → 用**固定容量最大堆**保留 top-`topk`（避免全排序）→
若 `pool_cap < 池大小`，用与现有随机注入同款的 xorshift 做**确定性采样**（保证可复现）。

### 4.2 改动：`ExperimentalBuildView`（**+1 字段，+1 分支**）

> `vamana_select` 的输入规模不变，成本对比才干净。

## 5. 守卫清单

| # | 守卫 | 判据 | 为什么 |
|---|---|---|---|
| **G1** | **基线同进程复现** | 同一次运行内 `batch_build_experimental_v2` 的 R@10 与冻结基线偏差 ≤ 1pp | 消除跨进程/跨重编译抖动（已实测 ~0.05pp），否则 A/B 不可比 |
| **G2** | **候选池合法性** | 每个候选 `v` 必须满足 `part_rank[idx*k + assign[v]] < j`，且 `v != idx` | 池约束是本实验的**定义**，违反即结论无意义 |
| **G3** | **注入点等价性** | `partition = None` 时，构建结果（边集）与未改动版本**逐位相同** | 证明"+1 字段/+1 分支"没有副作用 |
| **G4** | **候选规模一致** | 分区版与基线版的候选总数（进 `vamana_select` 前）差异 ≤ 5% | 否则成本对比不公平 |
| **G5** | **随机注入未被改动** | 分区版仍注入 128 个全局随机候选 | B2 只替换变量 ①（§1.1） |
| **G6** | **确定性可复现** | 同一配置跑两次，边集逐位相同 | 采样必须是确定性 xorshift，不能用 `rand::thread_rng` |

> **G3 最关键**：它是"最小侵入"这个设计的**证明义务**。做法：加一个 `T2_ASSERT_IDENTICAL=1`
> 环境变量，在两种模式下各建一次图并逐边比对（1M 规模约 2×40s）。

## 6. 成本计量方案

**主指标：建图墙钟 + CPU 时间**（`BuildProfile` 的 `total_cpu_ms`），因为这是最终要优化的量。

**副指标：候选评估次数**（需要插桩，可选）。若加，走 `BuildProfile` 同款模式：
新增 `AtomicU64` 计数器，`#[cfg(feature="ablation")]` 下启用，默认零开销。
**建议在 B2-1 时加**，因为它能把"算法工作量"与"实现质量"分离——
若分区版墙钟更慢但评估次数更少，说明瓶颈在别处（如 Cache/对齐），结论会完全不同。

**必须固定**：`RUSTFLAGS="-C target-cpu=native"`、线程数、`ef_construction`、
以及**同一进程内跑所有臂**（G1）。

### ★ §7.1 实测结果（2026-09-16，三次独立运行）—— 本节判据的裁决

**详细数据见 `t2-b2-result.md`。核心：**

| 臂 | 建图 | R@10（三次运行） | 判定 |
|---|---|---|---|
| ef_c=128（基线） | 1.00× | 97.54 / 97.55 / 97.56% | — |
| **ef_c=64** | **0.63–0.66×** | **97.20 / 97.24 / 97.22%** | **稳定达标（−0.32pp）** |
| ef_c=32 | 0.56–0.57× | 96.34 / 96.47 / 96.63% | **骑在门槛上，掷硬币** |
| ef_c=16 | 0.46–0.47× | 92.12 / 92.55 / 92.26% | 不达标 |

- **固定成本地板 = 0.46×**（ef_c=16 墙钟）⇒ PiPNN 可争夺空间仅 **1.39×**
- **平凡解 `ef_c=64` 已达成 P3**（0.64× ≤ 0.70× ∧ 97.22% ≥ 96.55%）**且零代码**

⇒ **本节的预注册判据裁定为第一行（靶点消失 ⇒ 停止 T2）**：
设计文档未预设"更宽松的臂（ef=64）已达成 P3"，而它实际发生了。
按判据**精神**（防自欺）取第一行。

⇒ **B2-1 不再执行**。理由：B2-1 需要击败的不是 1.00×/97.55%，而是
**0.64×/97.22% 的平凡解**，而它的候选获取本身约 2.4× 更贵（§1.2）——
1.39× 的空间装不下 2.4× 的成本，且 B2-2 的实现成本（M1–M4）远超期望收益。

> 本文档 §4–§6 的代码改造设计**保留**：若将来在**冷层/SSD 场景**（f32 非驻留）
> 或**更大规模（N ≫ 1M）**下重估，`PartitionCtx` + 单分支注入点的设计仍可直接复用。

## 8. 风险与未知

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| **U1** | 7.8 万次/节点是**反推**，基数可能错 | B2 的成本对比判据会偏 | B2-0 的 ef 扫描给出斜率，可实测标定；必要时加评估计数器（§6） |
| **U2** | 分区池的**扫描内存局部性**远差于束搜索（束搜索沿图走，有空间局部性；池扫描是随机跳） | 即使评估次数相同，墙钟也可能更慢 | B2-1 必须**同时报评估次数与墙钟**，否则会把内存效应误判成算法效应 |
| **U3** | 单层图的混淆（C6） | 冻结基线与 PiPNN 同为单层 ⇒ 可比；但结论不能外推到多层 | 报告中显式限定"仅单层图" |
| **U4** | `vamana_select` 的输入分布变了（池候选的距离分布与束搜索候选不同） | α=1.2 的剪枝行为可能不再最优 | B2-1 附一条 α ∈ {1.0, 1.2} 的敏感性 |
| **U5** | 采样池（B2/B3 臂）引入随机性 | 召回可能不稳 | G6 确定性 xorshift；多条种子取均值 |
| **U6** | 分区未均衡（C4） | k=16 的 max/min=2.1 尚可，但若换 k 会恶化 | B2 固定 k=16；均衡化分区器留给 B3 |
