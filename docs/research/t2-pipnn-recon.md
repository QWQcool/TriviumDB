## 0. 结论摘要

| # | 结论 | 证据 | 对 PiPNN 的含义 |
|---|---|---|---|
| **C1** | 批量建图 **81.35%** 的时间花在 **beam search 寻路**；反向剪枝只占 5.49%，**锁争用 0.03%** | `BuildProfile` 五段式（§2） | ✅ **靶点对了**——但靶子不是"反向剪枝"，而是"全局束搜索取候选" |
| **C2** | 建图并行效率已达 **26.9× / 32 线程（84%）** | 964s CPU / 35.86s 墙钟 | ⚠️ **PiPNN 的"更多并行"收益几乎耗尽**（上限仅 ~1.2×）。它必须靠**减少每节点工作量**取胜 |
| **C3** | 现有图的边有 **32.4%（k=16）～53.4%（k=256）跨分区** | 冻结 1M 图 + k-means（§4） | ⚠️ 纯分区内构边会丢掉 1/3～1/2 的边；**桥接负担随 k 单调上升**，与并行收益直接对撞 |
| **C4** | k-means 在 k=256 时分区**极不均衡**（max/min = **8819**，最小分区仅 1 个点，gini 0.261） | §4 | ❌ 各向异性数据下，高 k 需要**均衡化分区**，否则负载失衡 + 空转线程 |
| **C5** | 增量 `insert` 中位 **577–682 μs**，**与 N 无关**；但尾部随 N 恶化（p99 4.4ms→16.2ms，max 33.7ms→**119ms**） | §3 | ⚠️ 119ms 尾部疑似 `layer0` Vec 扩容触发 **1GB memcpy**——这是**可低成本修掉的工程缺陷**，不是算法问题 |
| **C6** | 生产批量路径 `batch_build_from_store` 实际是**单层图**（`upper_layers.clear()` + `entry_point≡0`） | `quiver.rs:2360-2362`、`:641/:704` | ⚠️ **重大混杂因素**：PiPNN 单层 vs 现基线单层可比，但与 `insert`（多层 HNSW 式）**不可比** |

**一句话**：T2 的靶点（81% 的束搜索）比 bootstrap 报告设想的更准，但 **C2 砍掉了"靠并行取胜"这条路**，
**C3/C4 把 PiPNN 的代价量化出来了**——接下来必须做一个**真正构造分区图并测召回**的实验（§7），
而不是继续靠间接指标推断。

## 1. 图构建链路（代码地图）

### 1.1 邻接存储

| 项 | 事实 | 位置 |
|---|---|---|
| 结构 | `FlatAdj { data: Vec<u32>, stride }`——**定长数组的数组**（非 CSR） | `quiver.rs:200-203` |
| 布局 | 每节点占 `stride` 槽：`[degree, n0, …, n_{stride-2}]`，空槽哨兵 `EMPTY_NB = u32::MAX` | `:198`、`:367` |
| **stride** | **`m0*2+1` = `4m+1`**（m=32 → 257），即容量 `4m`，**2× headroom** | `:1010` |
| ⚠️ 注释错误 | `:195` 注释写 `stride = m0+1`，与实际的 `m0*2+1` **不符** | `:195` vs `:1010` |
| 并发版 | `ConcurrentFlatAdj`（`UnsafeCell<u32>` + `unsafe impl Sync`） | `:424-430` |
| 度 | 惰性路径可涨到 `4m=256`，`final_prune` 后收敛到 `m0=64` | `:781-804`、`:817-834` |
| 接口 | **无删边**；只有 `push_neighbor_raw`（追加）、`set_neighbors_*`（整体替换） | `:387/:397/:505/:521/:537` |

> 2× headroom 是惰性剪枝的**前提**：先无脑追加，容量耗尽才剪一次。这决定了 PiPNN 若要改度上界，
> 必须同时改 `stride` 语义（`:1010`）与加载侧的重建逻辑（`:3108-3111`，`stride` **不写入文件**）。

### 1.2 三条构建路径

| 路径 | 位置 | 并发 | 反向剪枝 | 层次 |
|---|---|---|---|---|
| `batch_build` | `:2140-2305` | Phase3 **完全串行** | 急式 | HNSW 式多层 |
| `batch_build_experimental` | `:2533-2689` | 裸指针别名 + `par_iter` | 急式（并行） | HNSW 式多层 |
| **`batch_build_experimental_v2`** | `:2316`/`:2434-2531` | **分轮(chunk=256) + 节点并行** + `StripedSpinLocks` | **惰性** + `final_prune` | **单层** |
| **`batch_build_from_store`** | `:2326-2408` | 同 v2 | 惰性 + `final_prune` | **单层** |

- **唯一生产入口**是 `batch_build_from_store`（`memtable.rs:1442`）；`bench_cohere1m` 默认走 `batch_build_experimental_v2`（`bench_cohere1m.rs:397`）→ **冻结基线是单层图**。
- 单层的证据：`:2360 self.entry_point = 0`、`:2361 self.max_level = 0`、`:2362 self.upper_layers.clear()`，
  且束搜索入口**硬编码为 0**（`:641`、`:704`）。

### 1.3 增量插入 `QuIVer::insert`（`:1033-1211`）

| 步骤 | 行号 |
|---|---|
| push 签名/ids/slot/tombstone、`random_level` | `:1034-1045` |
| 扩展 `layer0` / `upper_layers`（**`while len < level` 自动增长**）/ `visited.grow` | `:1048-1062` |
| 首节点短路 | `:1064-1068` |
| 高层贪心下降（纯 BQ 距离） | `:1070-1097` |
| 高层束搜索 `beam_search_upper` | `:1099-1106` |
| 逐层 `l = level..=0`：束搜索 → `vamana_select` → 正向建边 → **反向对每条边跑完整 `vamana_select`** | `:1108-1205` |
| `entry_point` 更新（仅 `level > max_level`） | `:1207-1210` |

- **急式（eager）**：`:1141-1167` 对 `selected` 里**每条**反向边都构造 `nb 现有邻居 + idx` 并跑一次完整
  `vamana_select` → 单次插入 `O(m0 · m0² · C) = O(m0³·C)`（C = ⌈dim/64⌉ = 12）。
- **`&mut self` 独占、无内部锁** → 天然单线程，并发由 `MemTable` 写锁串行化。
- **调用方**：`memtable.rs:813`（`insert`）、`:884`（`insert_with_id`）、`:1543`/`:1557`（WAL 重放）、`:2537`（`update_vector`）。

### 1.4 `vamana_select`（`:1626-1671`）

```rust
fn vamana_select(sigs: &Bq2Store, target: u32, candidates: &[(u32, u32)],
                 max_k: usize, dim: usize, alpha: f32) -> Vec<u32>
```

- 判据（`:1646-1649`）：若存在已选 `s` 使 `d(cid, s) < alpha · d(cid, target)`，则丢弃 `cid`。
- **距离是 BQ2 汉明（u32），不是 f32**（`sigs.distance`，`bq.rs:1104-1116`）。
- 复杂度 `O(max_k²·C)`；选不满时有第二轮回填（`:1656-1668`）。

### 1.5 序列化

- Header 40B 含 `dim/n/m/m0/ef_construction/alpha/entry_point/max_level/dirty_count`；`FlatAdj` **原始 memcpy**（`n × stride × 4B`）。
- `QUIVER_VERSION = 1`（`:2864`），加载侧对**非 1 版本直接拒绝、无迁移路径**（`:3012-3020`）。
- `stride` **不写入文件**，由 `m0*2+1` 重建（`:3108-3111`）。
- `load_from_file` 用 mmap（`:2969-2973`），但 `load_from_bytes` **逐数组 `collect()` 到新 `Vec`**（`:3092-3174`、`:3233-3242`）
  → **"名为 mmap 实为逐数组拷贝"确认成立**（与 `bootstrap-report.md` R2 一致）。

## 2. 建图成本分解（★ C1：81% 是束搜索）

`T2_N=1000000`，m=32/ef_c=128/α=1.2，惰性剪枝，32 线程，`TRIVIUM_BUILD_PROFILE=1`：

| 阶段 | CPU ms | 占比 |
|---|---|---|
| **束搜索寻路 / beam search** | **784,240** | **81.35%** |
| 前向选边 / forward select | 97,732 | 10.14% |
| 反向剪枝工作 / reverse work | 52,936 | 5.49% |
| Bitset 分配 / allocate | 28,808 | 2.99% |
| **反向剪枝锁等待 / reverse wait** | **335** | **0.03%** |
| 合计 | 964,051 | 100.00% |

- 墙钟 **36.92s**，27,084 vec/s（探针本身有开销；无探针时 34.43s / 29,043 vec/s，守卫1 允许 ±8%）
- **CPU/墙钟 = 964,051ms / 36,920ms = 26.1×**（32 线程）→ **并行效率 ~82–84%**

### 2.1 这修正了什么

`bootstrap-report.md` R4 把靶点定在"`insert` 的急式 `O(m0³·C)` 反向重剪"。**实测表明这不对**：
反向剪枝**只占 5.49%**，且惰性剪枝 + 条纹锁已把**锁争用压到 0.03%**。

真正的 81% 是**为每个节点跑 `ef=128` 宽度的全局束搜索来获取候选**。
PiPNN 的机制恰好是"用分区内局部搜索替代全局图遍历取候选"——**靶点是对的，只是不是 R4 说的那个**。

### 2.2 但 C2 砍掉了"并行取胜"这条路

并行效率已 82–84%，即便做到完美并行也只再快 **1.16–1.22×**。
**所以 PiPNN 必须证明"分区内取候选比 ef=128 全局束搜索工作量更少"**，而不是"更并行"。

## 3. 增量插入现状（C5）

`bench_t2_build_recon` 阶段 C，先用批量建图到 N，再对后续向量逐个 `insert`，计时 200 次：

| N | 中位 | 均值 | p99 | 范围 | 批量每向量 | **增量/批量** |
|---|---|---|---|---|---|---|
| 200,000 | **682.3 μs** | 860.6 μs | 4,391 μs | [288.7, 33,749] | 21.2 μs | **32×** |
| 990,000 | **577.6 μs** | 1251.3 μs | 16,219 μs | [314.8, **119,053**] | 35.7 μs | **16×** |

- **中位延迟与 N 基本无关**（577 vs 682，大 N 反而略低）→ 印证主导成本是 `O(m0³·C)` 的**反向重剪**，
  它不依赖 N。这**支持** R4 关于复杂度的判断（虽然它在**批量**路径里不是瓶颈）。
- **尾部随 N 显著恶化**：p99 4.4ms → 16.2ms，max 33.7ms → **119ms**。
  119ms 的量级与"`layer0`（1M × 257 × 4B = **1.03 GB**）触发一次扩容 + memcpy"吻合。
  → 这是**可低成本修掉的工程缺陷**（预分配 / `Vec::reserve` / 分块存储），不应混入算法对比。
- 外推：全量 1M 若纯靠 `insert` 建成，单线程约 **2 分钟（@200K）～10 分钟（@990K）**。
- **副产品（守卫证据）**：N=200K 时 `entry=200007`、N=990K 时 `entry=990007` → 插入确实触发了
  `entry_point` 更新（`:1207-1210`）；而 N=1M（无插入）时 `entry=0` ✓

### 3.1 批量建图后 `insert` 的语义陷阱

`batch_build_from_store` 设 `max_level=0` 且清空 `upper_layers`。此后 `insert`：
- **不会 panic**（`while upper_layers.len() < level` 自动增长 `:1051-1054`；`ul_idx < len` 守卫 `:1076`）
- 但**上层起点是空图**：`beam_search_upper` 返回空（`:1103` 有 `is_empty` 守卫），上层边**惰性长出**
- ⇒ 批量建图 + 增量插入得到的层次结构，与**纯 insert 建成**的层次结构**不同构**。
  任何"层次质量"对比必须先对齐这个前提。

## 4. 分区质量预实验（C3/C4）

**方法**：对冻结的 1M 图（`bench_t2_build_recon` 导出 L0 CSR，n=1M / 64M 有向边 / 平均度 64.0 / entry=0）
做 k-means 分区（50K 采样拟合，全量 assign），测三个量。对照组为**随机哈希分区**。

| 分区方案 | 跨分区边率 | 本分区召回上界 | J=5 | J=10 | J=25 | 分区 max/min | gini |
|---|---|---|---|---|---|---|---|
| 随机哈希 k=16 | 93.8% | 6.7%（期望 6.2%） | — | — | — | 1.0 | 0.000 |
| 随机哈希 k=64 | 98.4% | 1.7%（期望 1.6%） | — | — | — | 1.0 | 0.000 |
| 随机哈希 k=256 | 99.6% | 0.5%（期望 0.4%） | — | — | — | 1.0 | 0.000 |
| **k-means k=16** | **32.4%** | **70.0%** | **97.3%** | 99.7% | 100.0% | **2.1** | 0.130 |
| **k-means k=64** | **43.0%** | **59.3%** | **91.6%** | 97.2% | 99.6% | 4.0 | 0.165 |
| **k-means k=256** | **53.4%** | 50.2% | 82.6% | 90.7% | 96.8% | **8819.0** | 0.261 |

> **指标管线自检**：随机对照精确落在 `100/k %`（6.7 vs 6.2、1.7 vs 1.6、0.5 vs 0.4）→ 管线正确 ✓
>
> ⚠️ **勘误（本次自查抓到）**：初版脚本用 `assign[q_idx]` 当"查询所属分区"，而 `q_idx = arange(1000)`
> 是**训练集**下标，测出的是"训练向量 i 所在分区"，得到无意义的 6.1/1.6/0.5%。已修为
> `assign_to(qn, cent)`（查询**自身**的分区），正确值即 J=1 列。

### 4.1 C3：跨分区边率 32%→53%（随 k 单调上升）

- **32.4% @ k=16**：纯分区内构边会丢掉约 **1/3** 的边。
- **53.4% @ k=256**：丢掉过半。
- **趋势是关键**：分区越多 → 并行粒度越细 → **但跨分区桥接负担越重**。
  这与 C2（并行已 84%，上限仅 ~1.2×）叠加后意味着：
  **PiPNN 在"更多分区"方向上同时失去并行收益、并增加桥接成本** —— 最优点可能在**低 k**（16~32）。

### 4.2 C4：k=256 分区极不均衡（max/min = 8819）

数据已实测各向异性（`l1-followup.md`），k-means 在高 k 下产生**最小仅 1 个点**的分区，
最大 8,819（均衡值应为 3,906）。gini 0.130 → 0.165 → 0.261。
→ 高 k 必须配**均衡化分区**（等频分位 / 递归中位切分 / 容量约束 k-means），否则并行负载失衡、
小分区空转线程，会直接抵消分区带来的收益。

### 4.3 本节的解释边界（必须声明）

「本分区召回上界」测的是**搜索**限制在本分区内的天花板。**PiPNN 并不限制搜索**——
它是在**构建**时用分区内候选，随后用跨分区边**缝合**，搜索仍全局遍历。
所以 50–70% **不构成 PiPNN 的反证**。

真正有约束力的是 **C3 的跨分区边率**：它量化了"缝合必须补回多少边"。
要判定 PiPNN 是否可行，必须做 §7 的**真构造实验**，而不是继续用间接指标推断。

## 6. 风险与未知

| # | 项 | 影响 | 处理 |

| **U1** | **单层 vs 多层的混淆** | 生产路径单层、`insert` 多层，"vs Vamana/PiPNN"的对比前提不成立 | 先做**单层 vs 多层消融**（`bootstrap-report.md` R7），并把基线钉在单层（=冻结基线） |
| **U2** | **C3 只测了"现状图的边局部性"** | 未证明分区内候选**不能**产生等价边 | §7 的真构造实验 |
| **U3** | **跨分区边率依赖分区器** | k-means 只是一个选择；不同分区器差异未知 | 已用随机对照校准量级；后续可加 RP-tree / 均衡分位 |
| **U4** | **PiPNN 论文的超参未对齐** | 分区数、代表点选择、缝合策略都可能不同 | 严格按论文 §实现细节复现，并做超参敏感性 |
| **U5** | 高 k 分区不均衡（C4） | 会抵消并行收益 | 用均衡化分区，或在实验里显式报告负载失衡 |
| **U6** | 增量插入的 `upper_layers` 语义（§3.1） | 层次质量对比不可比 | 对比时统一用"批量建图+增量"或"纯 insert"其中一种 |

## 7. 下一阶段行动清单

### 7.1 T2-B（决定性实验）：真构造分区图并测召回

**目标**：判定"分区内取候选 + 跨分区缝合"能否在**更少工作量**下达到现有 graph 的召回。
必须**真的构造图**，不能再用间接指标。

设计（建议分三步，每步都有独立结论）：

| 步 | 内容 | 判定标准 | 成本 |
|---|---|---|---|
| **B1** | **边一致性对拍**：对**采样节点**（如 5K），比较 ① 现有束搜索选出的 `m0` 邻居 vs ② 分区内精确 top-`m0`（同分区 + J 个邻接分区候选池） | 邻居集合**重叠率** ≥ 70% ⇒ 分区内候选可替代全局束搜索 | 中（需精确 KNN，可限制在采样分区） |
| **B2** | **端到端构造**：用 ② 的边构一张分区图 + 缝合，**复用现有 `search_flat`** 测 R@10/QPS | R@10 相对冻结基线（97.55% @ ef=128）**退化 ≤ 1pp** 且**建图 CPU 显著下降** | 高（需新增构建路径 M1–M4） |
| **B3** | **超参扫描**：k ∈ {16, 32, 64} × 缝合宽度 × 分区器（k-means / 均衡分位） | 找最优点；验证 C3 的"低 k 更优"预测 | 中 |

**建议先做 B1**：它最便宜、且能**证伪**整条路线（若重叠率 < 40%，说明分区内候选质量远不及全局束搜索，
PiPNN 在此数据上不成立，可立即止损）。

### 7.2 前置工程项（与算法解耦，可先行）

| 项 | 价值 |
|---|---|
| **D3 修 `layer0` 扩容抖动** | 消除 119ms 尾部，让增量插入的对比干净 |
| **D4 修 `load_bytes` 真零拷贝** | 冷热实验（`bench_ssd_cold_hot`）的前提 |
| **U1 单层 vs 多层消融** | 钉死对比前提 |
| **D1/D2 注释修正** | 低成本、消除后续误读 |

### 7.3 建议

**先做 B1（边一致性对拍）**，因为它是最便宜的可证伪实验，且直接决定 T2 是否值得进入 B2 的重构投入。
若 B1 通过（重叠率 ≥70%），再做 D3（修抖动）+ B2；若 B1 失败，T2 应转向
"保留全局束搜索、只优化其**常数因子**"的方向（例如把 81% 的束搜索内核从 BQ2 标量升级为 SIMD）。
